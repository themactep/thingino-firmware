# Why `ota-rootfs` leaves a camera pingable but unreachable

Investigation, 2026-08-20. Source-only analysis of this tree (branch `ciao`),
no camera access. Every claim below carries a file:line; the "not established"
notes at the end are as important as the findings.

Context: after `make ota-rootfs` a camera repeatedly ended up answering ICMP
while refusing SSH (`Connection reset` during key exchange), needing a manual
power cycle. Observed on 2026-08-20 on a wuuk_y0510_t31x_sc4336p_ssv6158:
several minutes of ping-yes / ssh-no, then an uptime of 9 seconds — so the
board had reset a second time.

## The failure chain

1. **The host never checks the data image against the device.**
   `scripts/fw_ota.sh:437-458` pads `rootfs.squashfs` to 64k (`:442`, `:446`)
   and passes `data.jffs2` through untouched. `/proc/mtd` is never read, no
   target size is compared. Even the squashfs handling is padding, not a check.

2. **On the device, data is flashed after rootfs, and its failure aborts
   before the reboot.** `package/thingino-sysupgrade/files/flash-ota:115`
   writes rootfs, `:117` writes data with `|| exit 1`, `:128` is the
   `reboot -f`. A failing data write never reaches line 128 — **there is no
   reboot**.

3. **`flashcp` refuses an oversized image before the first erase.** busybox
   1.38.0 as built here (patched for `-A` by
   `package/all-patches/busybox/1.38.0/0110-flashcp-add-erase-all-flag.patch`)
   fails with `bigger than` when `st_size > mtd.size`. Measured case:
   `data.jffs2` 10158080 B against a 9502720 B partition. **The data partition
   is therefore never touched** — which is why the overlay survived intact and
   dmesg showed no jffs2 errors.

4. **But rootfs has already been overwritten underneath the running system.**
   `flash-ota:76-90` clones busybox into tmpfs and tries
   `mount -o remount,ro /`; neither prevents the MTD backing the mounted
   squashfs from being erased. From that point every page-in of `/` serves
   bytes of the *new* image to processes of the *old* one. Processes die as
   soon as they touch a non-resident page. The kernel and network keep
   running (ping answers), the dropbear listener still accepts TCP, and the
   forked child dies during key exchange — exactly the observed symptom.

5. **The host swallows the error and reports success.**
   `scripts/fw_ota.sh:495` runs the flash command with `|| true` and `:497`
   unconditionally prints "Done. Camera is rebooting." The `/tmp/needs_reboot`
   marker is set in rootfs mode (`:488`) but only evaluated in full mode
   (`:385-394`).

6. **The second reboot is an emergency reset, not part of the flow.** Two
   candidate paths, both present: the busybox hardware watchdog started at
   sysinit (`overlay/etc/inittab:16` → `overlay/etc/init.d/K99watchdog:23-24`,
   60 s default; `rcK:15-21` documents that killing the daemon triggers the
   hardware reset), and the kernel panic path (`panic=${panic_timeout}` with
   `panic_timeout=2`) if PID 1 dies on paging. Nothing schedules a planned
   second reboot: `F02failsafe` waits 2 s for a keypress, `S97sysupgrade` only
   sets `fw_setenv sysupgrade_complete`.

7. **A changed SSH host key after a *successful* `ota-rootfs` is expected**:
   the key lives under `/etc/dropbear/` in the overlay
   (`overlay/etc/init.d/S50dropbear:6,29-31`), and the mode always writes a
   fresh `data.jffs2`. That the key survived on 2026-08-20 is further evidence
   the data write never happened.

## Root cause

`data.jffs2` is padded to exactly `DATA_PARTITION_SIZE`
(`Makefile.utils:164-165`). The partition sizes are computed from the image
size at U-Boot build time, so a rebuilt image produces a differently sized
data image — which can never fit the partition an older full flash laid down.
`flashcp` then refuses it, `flash-ota` exits before its reboot, and the board
is left executing from a rootfs that no longer exists underneath it.

jffs2 does not need that padding: `--pad` without a size (eraseblock aligned)
plus `flashcp -A`, which erases the whole partition anyway, would make the
data image layout-independent. *Plausible, untested.*

## Partition layout: what is and is not adjustable

* **`mtdparts` at runtime comes solely from the saved U-Boot environment.**
  `bootcmd` builds `bootargs` with `mtdparts=${mtdparts}` (generated by
  `Makefile.utils:227-228`). The value compiled into the binary is only the
  default env block (`CONFIG_DEVICE_ENV`, produced by
  `scripts/uboot-device-env.sh` from the `THINGINO_PATCH_DEV_ENV` hook,
  `package/thingino-uboot/thingino-uboot.mk:135-153`) and applies only when
  the stored env is missing or CRC-invalid. **The saved env wins.** The `sed`
  on `CONFIG_MTDPARTS_DEFAULT` at `thingino-uboot.mk:148` is a no-op for the
  2013.07 U-Boot on this camera — the symbol is not in that header.
* **`fw_setenv mtdparts '...'` therefore moves the boundary without touching
  U-Boot itself.** `data_addr`/`data_size` must move with it — the U-Boot
  factory reset erases by those values (`Makefile.utils:195,224-225`), so
  wrong ones wipe the wrong region. Writing the env partition with the
  on-board tool is a different act from patching or rebuilding U-Boot, but if
  the saved env is ever lost, U-Boot falls back to a compiled-in default that
  may describe a different layout — keep the two consistent.
* **`BR2_PACKAGE_THINGINO_UBOOT_MTDPARTS` (`package/thingino-uboot/Config.in:109`)
  is a dead switch.** Declared and never consumed, here or in
  `upstream/master`; the same holds for `..._BOOTARGS`. Setting it does
  nothing.
* **Cutting rootfs with slack is a one-line change.** Everything derives from
  `ROOTFS_PARTITION_SIZE = $(ROOTFS_BIN_SIZE_ALIGNED)` (`Makefile:389`, 64k
  alignment) and flows consistently into mtdparts (`Makefile:399-400`,
  `Makefile.utils:227`), the full-image dd, the data padding
  (`Makefile.utils:164-165`) and the baked U-Boot default
  (`thingino-uboot.mk:139-146`, which would need the same rounding). Rounding
  up to, say, the next 1 MB costs exactly that slack from data — irrelevant at
  96% free — and squashfs ignores trailing erased space. Nothing in the source
  breaks; it takes effect only once a device has moved to the new layout.
* **jffs2 across a layout change:** if data only grows at its end (same
  offset), the contents survive — jffs2 scans and adopts the empty blocks. If
  the *offset* moves, the start is overwritten by the new rootfs and it is
  effectively a reformat; `overlay/init:15-21,37-43` formats on mount failure
  anyway. `make backup-overlay` (`Makefile.ota:246-250`) exists as the rescue
  path.
* **Upstream has the same behaviour.** `flash-ota` is diff-identical with
  `upstream/master`; the dynamic sizing comes from upstream commit
  `e08b02942` (2026-08-07), which fixes boot/env/backup/kernel but leaves
  rootfs cut exactly to the image. No public issue or discussion on a movable
  rootfs/data boundary was found — absence is not proof.

## Not established

Which reset path actually fired on 2026-08-20 (watchdog vs. panic); whether
`watchdog_enabled` is true on that device; why the hang lasted minutes rather
than seconds (depends on page-cache residency). Serial capture during a
deliberate reproduction would settle all three.

## Decision

The flashing procedure is deliberately left unchanged (2026-08-20). The
operational rule instead: **always `make ota`, never `ota-rootfs`** — see the
memory note and timps `docs/flash-footprint-srt-2026-08-20.md`.

## A second way to flash the wrong thing: the packed image lags the build

`make ota` installs whatever `images/*.bin` currently holds, and two separate
mechanisms let that file hold a binary older than the source tree.

**Buildroot will not rebuild a package whose stamp is valid.** With
`TIMPS_OVERRIDE_SRCDIR` set, committing and tagging in the timps checkout does
not invalidate `.stamp_built`. A plain `make` then repacks fresh images around
the *previous* binary. Measured 2026-08-21: `make` after tagging v1.9.2
produced images dated 14:12 containing a v1.9.1 `timpsd`, byte-identical to the
one built at 10:37. Use `make rebuild-<pkg>` (dirclean + build + reinstall).

**Within one make run the images are packed before the forced install lands.**
Running `make rebuild-timps && make` is still not enough: on 192.0.2.102 the
squashfs was written 14:24:30 and `target/usr/bin/timpsd` at 14:25:28 — the
image predates the binary it was supposed to contain. The pack has to happen in
a *separate* invocation, after the rebuild has fully settled.

Neither failure is visible from the outside. The image is freshly dated, the
build exits 0, and on one board both versions even had the same file size
(274100 B), so a size check would have passed too. The only reliable check is to
read the binary back out of the packed image:

    unsquashfs -q -d /tmp/x -f images/rootfs.squashfs usr/bin/timpsd
    strings /tmp/x/usr/bin/timpsd | grep -m1 '^v[0-9]'

Do that before every flash, and loop the pack step until it matches. Timestamps
and file sizes are not evidence here; the extracted version string is.
